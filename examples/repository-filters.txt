# Which repositories make up your estate.
#
# Copy this to config/repository-filters.txt and edit. `knowledgestore discover`
# reads it, lists your GitHub organisation, and writes the repositories that
# match to config/repositories.txt.
#
# Three rules, one per line. No regex and no fuzzy search: this file is meant to
# be read and reviewed in a pull request, so what is in the estate is a decision
# with a diff, not the result of a search that quietly changes.
#
#   prefix <name-prefix>    include every repository whose name starts with this
#   repo <exact-name>       include one repository by name
#   team <github-team-slug> include every repository the GitHub team has
#   exclude <exact-name>    exclude one repository, even if another rule matched it
#
# `exclude` always wins. Archived repositories are always excluded, so you never
# need a rule for them.
#
# Comments and blank lines are ignored. Comment your reasoning: whoever widens
# the estate next will want to know why something was left out.

# --- Start with the naming conventions that define your estate -------------
# Most estates have one or two prefixes covering the bulk of them.
prefix myteam-service-
prefix myteam-ui-

# --- Or define the estate by ownership --------------------------------------
# Teams without naming conventions - and infrastructure estates - cannot be
# expressed as prefixes. A team rule includes everything the team has, so an
# estate can simply be "what my team owns". Excludes still win, which is how
# you keep a team's terraform scaffolding out while taking its services.
team my-github-team

# --- Add what the conventions miss -----------------------------------------
# Repositories predating the naming scheme, shared libraries, or the E2E suite
# when it sits outside the pattern. E2E suites are worth including: their
# specifications and page objects are the estate's business documentation.
repo legacy-payments-api
repo myteam-e2e-tests
repo shared-component-library

# --- Exclude what a prefix wrongly caught ----------------------------------
# Infrastructure, scaffolding, retired services and generated repositories add
# nodes without adding meaning. Say why, and when.
exclude myteam-service-deprecated       # retired 2026-01, kept for audit only
exclude myteam-ui-terraform             # infrastructure, no application code

# --- Growing the estate later ----------------------------------------------
# Adding repositories re-clusters the graph, which moves community ids, so
# existing community summaries need remapping or regenerating — the
# knowledge-store-build skill covers how.
#
# Prefer deliberate batches over importing everything an organisation happens
# to contain: a larger graph is not automatically a more useful one, and every
# repository costs clone time, build time and clone weight for consumers.
#
# An order that works:
#   1. the applications and services your users' journeys actually touch
#   2. the shared libraries those depend on
#   3. adjacent services, one batch at a time, when real questions reach them
